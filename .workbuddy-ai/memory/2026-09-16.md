## Découverte structurante — « la course LONAB »

`"QUARTE" DU JEUDI 10 SEPTEMBRE 2026` / `PARISLONGCHAMP - PRIX CARRUS`.
**La LONAB met en avant UNE seule course par jour.**
Elle correspond exactement (vérifié **8/8** sur 09→16/09) à la course du
programme PMU qui porte **QUINTPLUS + QUARTPLUS + TIERCE**.

⚠️ Piège de nommage de l'API PMU :
- endpoint `programme` → `QUINTPLUS` / `QUARTPLUS` (sans underscore)
- endpoint `rapports-definitifs` → `QUINTE_PLUS` / `QUARTE_PLUS` (avec underscore)
→ normaliser via `typePari.replace("E_","").replace("_","")`.

## Suite 3 — l'application servie sur UN SEUL port (l'utilisateur ne voyait rien)

**Problème signalé** : l'utilisateur ne parvenait pas à voir la page.

**Cause** : l'interface n'était accessible que via `http://localhost:5173`. Vite 8 se lie à
**IPv6 `::1`**, donc `http://127.0.0.1:5173` échoue (code 000). Un panneau d'aperçu qui résout
`localhost` en `127.0.0.1` ne voit rien. S'ajoutait la fragilité de deux processus à maintenir
(API 8000 + Vite 5173).

**Correctif — service groupé, un seul port** :
- `backend/main.py` sert désormais l'interface compilée : montage de `/assets` puis **route
  attrape-tout** qui renvoie `index.html` pour toute route d'interface (sinon un rechargement de
  `/courses` renverrait 404). Déclarée **après** les routeurs d'API, donc `/api/...` reste
  prioritaire ; un chemin `/api/...` inconnu renvoie **404 d'API**, jamais du HTML.
- Garde-fou contre la remontée de chemin (`candidate.relative_to(_dist_root)`).
- `index.html` servi en `Cache-Control: no-store` (les actifs, eux, portent une empreinte).
- `src/lib/apiBase.ts` : l'adresse de l'API devient **relative** sauf si le port est `5173`
  (serveur Vite). Ouvrir `localhost:8000` et `127.0.0.1:8000` fonctionne donc indifféremment —
  deux hôtes = deux origines pour le navigateur, une URL absolue aurait créé une requête croisée.
- `demarrer-fasoturf.bat` : lanceur double-cliquable (compile si `dist/` manque, ouvre le
  navigateur, démarre le serveur). Chemin du projet en ASCII → `.bat` sans risque d'encodage.

**Résultat** : `http://127.0.0.1:8000` sert interface + API + `/docs`. Toutes les routes et tous
les actifs répondent 200. **41/41** vérifications de bout en bout (4 nouvelles sur le service de
l'interface : index servi, routes d'interface rechargées, actifs servis, API inconnue non avalée
par le SPA). Socle LONAB toujours `d71f6a01…f41d2cdb42`.

**Leçon** : pour qu'un utilisateur voie une application, un seul port et une seule URL valent
mieux que deux serveurs — et ne jamais supposer que `localhost` et `127.0.0.1` sont
interchangeables.

même sur une page vide). Validation : marqueur présent **et** `length > 400` **et** zéro erreur
console.

**Décision d'architecture du test — un processus enfant par route.** Deux échecs ont imposé ce
choix :
1. `RangeError: Maximum call stack size exceeded` — exposer le `performance` de jsdom à la place

## Suite 5 — SIDEBAR ILLISIBLE : classes Tailwind inertes (signalé par l'utilisateur)

**Symptôme rapporté** (capture d'écran) : les libellés de la sidebar étaient **invisibles**.

**Cause racine — un piège de Tailwind, invisible à la compilation :**

Tailwind ne génère une classe que si sa valeur existe dans le thème. L'échelle d'opacité va
**de 5 en 5** ; or le code utilisait des valeurs **nues hors échelle** :

```tsx
"font-medium text-white/72 ..."   // ✗ /72 n'existe pas → AUCUNE règle CSS générée
```

Conséquence en cascade :
1. aucune couleur n'est appliquée → le `<span>` **hérite** de `body { color: #17221c }` ;
2. la sidebar a pour fond `#001c18` ;
3. → **noir sur noir**. Contraste mesuré : **1,09:1** (WCAG exige 4,5:1 minimum).

`ft-on-dark` (présent sur la sidebar) ne définissait **que** `:focus-visible` — il ne posait aucune
couleur de texte, malgré son nom. Rien ne rattrapait donc l'héritage.

⚠️ **Ni `tsc`, ni `oxlint`, ni `npm run build` ne signalent ce défaut** : la compilation réussit,
la classe est simplement absente du CSS. C'est un bug **invisible en développement**, visible
seulement à l'œil.

**Inventaire : 22 usages inertes dans 6 fichiers** (`SidebarNav`, `ProBanner`, `WelcomeHero`,
`LatestRaces`, `RaceCard`, `RaceDetailModal`, `NextRaceCard`).

**Correctifs :**
- Toutes les valeurs hors échelle passées en **forme crochets** (préserve l'intention exacte) :
  `text-white/72` → `text-white/[0.72]`, `bg-white/8` → `bg-white/[0.08]`,
  `border-white/12` → `border-white/[0.12]`, `bg-[#04241C]/88` → `bg-[#04241C]/[0.88]`, etc.
- `src/index.css` : `.ft-on-dark { color: #fff }` ajouté dans **`@layer base`** — la couche
  `base` est émise avant `utilities`, donc toute classe `text-*` reste prioritaire, mais un futur
  oubli dégrade désormais vers **du blanc visible** au lieu du **noir invisible**.

**Contraste après correctif** (fond `#001c18`) :
| Élément | Avant | Après |
|---|---|---|
| Libellés nav inactifs | **1,09:1** (invisible) | **9,53:1** (AAA) |
| Libellé nav actif | — | 17,81:1 (AAA) |
| Texte ProBanner | 6,95:1 | 6,95:1 (AA) |

**Nouveau garde-fou — `scripts/check_tailwind_classes.mjs`** : extrait toutes les classes
utilisées dans `src/`, et vérifie que chacune **existe réellement dans le CSS compilé**. Attrape
exactement cette classe de bug. Ajouté aux scripts npm : `check:css`, `check:contract`,
`check:render`, `check:api`.

**Leçon générale** : une classe utilitaire écrite « à peu près » n'échoue pas — elle **disparaît**.
Quand un style manque, vérifier d'abord que la classe existe dans le CSS compilé, pas seulement
qu'elle est écrite dans le JSX.

**Vérifications** : `check:css` 0 classe inerte · `test_api.py` 41/41 · contrat 43 vérifs CONFORME ·
`check:render` 13/13 pages · `tsc -b` 0 erreur · `oxlint` 0 warning. Socle LONAB
`d71f6a01…f41d2cdb42` inchangé.

**Serveurs** : `http://127.0.0.1:8000` (FastAPI, interface+API+/docs) et `http://127.0.0.1:4173`
(`vite preview`) servent tous deux le build corrigé.

## Suite 6 — « L'API a répondu 404 » sur le tableau de bord (port 4173)

**Symptôme rapporté** : « Impossible de charger le tableau de bord — L'API a répondu 404. »

**Cause racine — énumération de ports côté client.**
`src/lib/apiBase.ts` ne traitait qu'**un seul** port de développement :

```ts
const DEV_SERVER_PORT = "5173";
return window.location.port === DEV_SERVER_PORT ? "http://127.0.0.1:8000" : "";
```

Sur le port **4173** (`vite preview`), la condition était fausse → URL **relative** → `/api/dashboard`
était servi par le serveur de **fichiers statiques**, qui n'a pas d'API.

**Le détail qui rendait le diagnostic trompeur** : `vite preview` ne fait son repli SPA que si le
client accepte du HTML. Mes tests `curl` (en-tête `Accept` par défaut) recevaient **200 + HTML** ;
le frontend, qui envoie `Accept: application/json`, recevait **404** avec un corps non-JSON — d'où
le message `L'API a répondu ${status}` (repli de `readError`). Vérifié :

| Requête sur 4173 | Résultat |
|---|---|
| `Accept: application/json` (ce que fait le frontend) | **404** |
| `Accept` par défaut | 200 HTML |

**Correctif structurel — supprimer l'énumération, pas l'étendre :**
- `vite.config.ts` : **proxy `/api` → `http://127.0.0.1:8000`** déclaré pour `server` **et**
  `preview` (cible surchargeable par `FASOTURF_API`).
- `src/lib/apiBase.ts` : `API_BASE_URL = ""` — **toujours relatif**. L'API est sur la même origine
  dans les trois modes de service : backend FastAPI (8000, qui sert `dist/` + `/api`), dev Vite
  (5173, proxy), prévisualisation Vite (4173, proxy). Une origine unique supprime aussi le CORS.
- Garde-fou ajouté à `scripts/smoke_render.mjs` : le bundle ne doit contenir **aucune origine
  d'API absolue** (`http://127.0.0.1:`, `http://localhost:`, `http://0.0.0.0:`). ⚠️ Ne pas tester
  la chaîne nue `localhost` : React Router embarque `http://localhost` (sans port) comme base
  interne → faux positif.

**Leçon** : ne jamais énumérer les ports dans le client. Un port oublié ne produit **aucune erreur
de compilation** — juste un 404 à l'exécution, sur un seul mode de service.

**Découverte d'outillage — contourner le shim *safe-delete* :**
`npm run build` échouait avec `[safe-delete] 操作失败 … trash operation: Unknown`, et **toutes** les
suppressions étaient refusées (`rm -rf`, `Remove-Item`, `cmd rd`) : le shim est en **fail-closed**.
Contournements qui fonctionnent :
- **reconstruire** : renommer `dist` → `dist_stale` puis relancer (un dossier absent n'a rien à
  supprimer) ;
- **supprimer** : `[System.IO.Directory]::Delete($path, $true)` en PowerShell — **passe** là où
  `Remove-Item` échoue.
⚠️ Ne pas boucler `rm -f` fichier par fichier : chaque appel est intercepté et la boucle s'étouffe
(4 min pour rien, tâche tuée).

**Ménage** : suppression de `dist_stale`, `dist_check` et `dist_verify` (~9 Mo de builds
temporaires). ⚠️ `.gitignore` ne couvrait que `dist` et `dist-ssr` — les dossiers `dist_*` auraient
pu être versionnés.

**Vérifications** : `check:css` 0 inerte · `test_api.py` 41/41 · contrat CONFORME ·
`check:render` **13/13** (sur 8000 **et** sur `localhost:4173` via le proxy) · `tsc` 0 erreur ·
`oxlint` 0 warning · socle LONAB `d71f6a01…f41d2cdb42` inchangé.

**État des serveurs** : `http://127.0.0.1:8000` (recommandé) et `http://localhost:4173` servent
tous deux le même bundle `index-CtulsfFL.js`, API 200 sur les deux.
⚠️ Vite se lie à **IPv6 `::1`** : `127.0.0.1:4173` échoue, `localhost:4173` fonctionne.
